## 0. 一句话定位

把现有「图书管理系统」升级为**闭环式 AI 学习规划智能体**：

**诊断 → 规划 → 配书 → 打分 → 验收 → 重排**。

首期只做两个场景：**技能自学**（如 Java 后端自学）和**阅读计划**（如读一本经典书）。场景全部写在配置文件里，以后加方向只加配置、不改代码。

### 1.2 本方案要补的缺口



1. **模型调用没有统一网关**：现在直接 `chatClientBuilder.build()`，强 / 弱模型不分档、无 Mock 抽象、无费用记账。

2. **学习计划是写死的**：没有诊断环节、没有 "模型拆学习点→JSON 校验→配书→排期" 的固定流水线。

3. **没有验收机制**：小测、自由练习 AI 点评、阅读复述都没做；不及格 / 漏打卡不会触发调整。

4. **重排是静默的**：AI 直接改库，没有 "先生成方案→用户确认→再执行" 的两步。

5. **场景写死在代码里**：自学和阅读计划应该配置化。

6. **资料问答**：要升级成 MySQL 全文检索 + 标出处 + 带最近 10 条记忆。

7. **没有管理员快进日期**：演示时没法把 "今天" 拨到下周看效果。

8. **没有前端**：要做 Vue3 + Vant 手机网页。

9. **没有 Docker Compose**：要一键起全栈。

## 4. 核心设计

### 4.1 模型调用网关 `ModelGateway`（T001–T003）

**目标**：全工程只有这一个地方发 LLM 请求，业务代码不直接碰 `ChatClient`。



```
public interface ModelGateway {
    /**
     * @param tier   STRONG（诊断/规划/点评）/ WEAK（打标/分类）/ MOCK（本地假数据）
     * @param scene  业务场景：DIAGNOSIS / PLAN / MATCH / REVIEW / CHAT / QA
     * @param prompt 完整 prompt
     * @return 统一结果，含文本 + token 用量
     */
    ModelResult chat(ModelTier tier, String scene, String prompt);
}
```

**三档配置**（`application.yml`）：



```
library:
  model:
    default-tier: STRONG          # 全局默认档
    profiles:
      strong:
        enabled: true
        model: ${AI_MODEL:deepseek-v3}
        base-url: ${AI_BASE_URL:https://api.openai.com}
        api-key: ${AI_API_KEY:dummy-key}
        temperature: 0.3
        input-price-per-1k: 0.0028   # 元/千 token，可配
        output-price-per-1k: 0.0084
      weak:
        enabled: true
        model: ${AI_MODEL_WEAK:deepseek-v3}
        input-price-per-1k: 0.0006
        output-price-per-1k: 0.0018
      mock:
        enabled: true              # 无 key 时自动切 mock
```

**自动降级规则**：



* `strong.api-key` 为空或等于 `dummy-key` → 自动走 `mock` 档，返回结构化假数据，全流程可跑。

* 真实调用抛异常 → 不重试 LLM（JSON 校验失败的重试在业务层做），直接抛 `AiUnavailableException`，由全局异常处理返回 503。

**Token 账本**：每次调用落 `ai_call_log`（改造后字段见 §5.1），记录 `tier / scene / cost`。账本接口返回：



* 总调用次数、总 tokens、总费用

* **节省比例** = `1 - 实际费用 / (若全部用 STRONG 档的理论费用)`，即 "因为 WEAK/MOCK 档省了多少钱"。

### 4.3 学习计划生成固定流水线（T005–T010）

严格按顺序，**任何一步失败都不静默降级**：



```
[1] 用户选场景 + 填目标
    → ModelGateway(STRONG, DIAGNOSIS) 出诊断题 JSON
[2] 用户答题
    → ModelGateway(STRONG, PLAN) 把目标拆成学习点 JSON
[3] 代码用 Jackson 校验 JSON Schema（必填字段、类型、数量上限）
    ├─ 校验通过 → [4]
    └─ 校验失败 → 重试 1 次（prompt 里附上次报错）
        ├─ 通过 → [4]
        └─ 再失败 → 模板兜底：按场景默认章节列表生成学习点，打标 fallback=true
[4] 代码给每个学习点配书：
    ├─ self-study：按 category_id + 学习点关键词在 book 表做全文检索，取 Top1
    └─ reading：直接绑用户选的那本书 + 按章节数均分
[5] 代码排期（不用模型）：
    从今天起按 dailyHours 把学习点铺到日历，周末/复习位用规则补
[6] 返回"计划预览"给用户，不直接落库
    → 用户点确认 → 才 insert study_plan / learning_point
```

**关键约束**：



* 第 \[2] 步模型必须输出**纯 JSON**（prompt 里强制 `Output ONLY JSON, no markdown fence`）。

* 第 \[3] 步失败重试只有 1 次，再失败走模板兜底，**绝不把模型输出当代码执行**。

* 第 \[5] 步排期纯代码，不让模型排日期（模型排期不可复现、不可控）。

### 4.3.1 排期器 `Scheduler`（纯 Java + 单元测试，T009 系列）

排期器是本项目的硬核部分，**不依赖任何框架、不碰 DB，全部可单测**。输入：学习点列表（含前置依赖、权重、预计学时）、每日可用时长、开始日期、截止日期（可空）、借书到期日（阅读计划才有）。输出：每个学习点的 `scheduledDate` + 每日时长统计。

**七条硬规则**：



1. **有截止日期就倒排**：从 `examDate` 往前铺，**最后 20% 的天数强制留作复习冲刺**（不排新学习点，只排复习）。

2. **先学前置内容**：学习点之间有 `prereqIds`，排期前做拓扑排序，前置未排完不能排后置；出现环直接报错。

3. **每日总时长 ≤ 用户设定**：一天里新学 + 复习的总小时数不能超过 `dailyHours`；超了就往后顺延，不允许硬塞。

4. **知识类复习走 FSRS**：见 §4.3.2。

5. **时间不够时的压缩策略**（按顺序）：

* 先压缩**低权重**学习点（`weight` 字段，模型拆分时给出，默认 1.0，核心概念 2.0），把 `estHours` 砍半；

* 还不够，再删掉 \*\*"没有被低估"\*\* 的学习点（即模型没标 `mustLearn=true` 的点），并在返回结果里带 `compactionWarnings` 提示用户 "已自动压缩 / 删除 X 个低优先级内容"。

1. **阅读计划不晚于借书到期日**：reading 场景下，最后一个学习点的 `scheduledDate` 必须 ≤ `borrowDueDate`；超了直接报错让用户续借或换薄书。

2. **复习积压暂停新内容**：如果某天待复习的学习点（dueDate ≤ 今天）数量超过阈值（默认 5），当天**只排复习、不排新学习点**，新内容往后顺延。

**所有规则都要有对应单元测试**：构造一个 10 个学习点、10 天、每天 2h 的场景，断言最后 2 天是复习日、前置依赖顺序正确、某天时长不超 2h、时间不够时压缩警告出现。

### 4.3.2 FSRS 间隔重复（T009b）



* 用开源 FSRS 算法的**天粒度简化版**（不做分钟级调度，不引入官方 JS 库，自己实现核心公式：每个学习点维护 `difficulty`(1-10)、`stability`(天)、`dueDate`、`reps`、`lapses`）。

* **验收得分 → 四档评分**：score ≥ 90 → `Easy(4)`；75–89 → `Good(3)`；60–74 → `Hard(2)`；< 60 → `Again(1)`。

* 新学完第一次复习固定按 **1 天、3 天、7 天** 排（FSRS 初始间隔），之后由 FSRS 公式根据 difficulty/stability 递推。

* FSRS 状态用 `toJson()` 序列化存 `learning_point.fsrs_state` 字段，不单独建表。

### 4.3.3 掌握度与五类页面状态（T009c）

掌握度分数 `masteryScore` 初始 0，按事件累加：



| 事件          | 分数变化           |
| ----------- | -------------- |
| 学完一个学习点     | **+10**（封顶 60） |
| 复习一次        | +5             |
| 验收通过        | +15            |
| 验收不通过       | **-20**        |
| 连续 3 天没动这个点 | -3（每日扫描任务触发）   |

**五类页面状态**（前端按这个渲染）：



| 状态  | 判定条件                                                 |
| --- | ---------------------------------------------------- |
| 未开始 | `scheduledDate > 今天` 且 `status=PENDING`              |
| 学习中 | `scheduledDate <= 今天` 且 `status=LEARNING`            |
| 待办理 | `dueDate < 今天`（复习过期）或 `scheduledDate < 今天` 仍 PENDING |
| 待巩固 | `masteryScore` 在 40–79 之间，且已验收过一次                    |
| 已掌握 | `masteryScore >= 80`                                 |

### 4.4 验收机制（T011–T014）



| 场景        | 验收方式                   | 怎么判分                                                         |
| --------- | ---------------------- | ------------------------------------------------------------ |
| 知识点小测（通用） | 模型出 5 道单选题，代码判分        | 对题数 / 5，≥60 分通过                                              |
| 技能自学      | 自由练习：用户提交一段练习文本 / 代码片段 | ModelGateway (STRONG, REVIEW) 返回 `{score, feedback, passed}` |
| 阅读计划      | 复述：用户提交一段复述文字          | 同上，模型打分 + 点评                                                 |

**不及格 / 漏打卡触发调整**：



* 小测 < 60 分 → 自动生成 `adjustment_proposal`。

* 当天任务没 DONE 且日期已过 → 次日定时任务（或管理员快进日期时）扫描，生成 `adjustment_proposal`。

* **AI 只生成方案，不直接改计划**（见 §4.5）。

### 4.5 重排 / 续借两步确认（T015）



```
AI 生成方案 JSON（哪些任务挪到哪天、为什么）
    → insert adjustment_proposal (status = PENDING_CONFIRM)
    → 前端弹卡片展示方案
    ├─ 用户点「确认执行」→ 后端按 proposal_json 真正改 study_task / learning_point，status = EXECUTED
    └─ 用户点「忽略」→ status = IGNORED，计划不动
```

**硬规则**：没有任何一条路径让 AI 直接 update 业务表；所有写操作必须经过 `adjustment_proposal` + 用户确认。

### 4.6 资料问答（T016–T017）



* 用 MySQL `FULLTEXT` 索引（`book.title/description`、`knowledge_document.content`），**不引入 ES**（比赛现场少一个组件少一份风险）。

* 回答末尾**必须标出处**：`—— 出处：《深入理解Java虚拟机》第3章 / 《借阅规则》第2条`。

* 结论式输出自动带上用户最近 10 条 `chat_message` 作为上下文（不是向量检索，是近期对话记忆）。

### 4.7 管理员：快进日期（T018）



* 业务代码取 "今天" 统一走 `ClockHolder.today()`，不直接 `LocalDate.now()`。

* `ClockHolder` 内部维护一个 `offsetDays`（默认 0）。

* 管理员接口：


  * `POST /admin/time/fast-forward?days=7` → offsetDays += 7

  * `POST /admin/time/reset` → offsetDays = 0

* 演示时一键拨到 "一周后"，漏打卡 / 逾期 / 复习位全部可见。

### 11.2 Mock 模式升级：按目标关键词路由（关键改动）

原方案 Mock 只返回一套 Java 假数据。**实际改成按用户输入 goal 的关键词动态路由**，让无 key 时也像智能体：

```
goal 含 "前端/web/vue/react"  → 返回前端学习路径（HTML/CSS/JS/Vue3/HTTP/综合项目）
goal 含 "python/爬虫/数据分析" → 返回 Python 路径（基础/文件/requests/pandas/FastAPI/数据看板）
goal 含 "产品/pm/运营"         → 返回产品经理路径（认知/需求分析/Axure/指标/PRD产出）
其他默认                      → 返回 Java 后端路径（基础语法/OOP/集合/MySQL/Spring Boot/MP/综合项目）
```

诊断题也跟着变（学前端问前端基础，学产品问产品经验）。**等 MoMA 充值后这一层直接删掉**，真模型会根据 goal 自由生成。

### 11.3 BookMatcher 实际策略

不是全文检索（book 表数据少），是**关键词映射 + LIKE**：

- JVM/虚拟机 → 匹配书名含"虚拟机"
- Spring → 匹配"Spring"
- 集合/异常IO/基础语法 → 匹配"Java核心"
- 算法 → 匹配"算法"
- 先按场景 categoryId 过滤，匹配不到降级不限分类
- 章节写死"第1章 {学习点标题}"，后续可接目录解析

### 11.4 /ai/qa 实际实现

- SQL: `MATCH(title, content) AGAINST (? IN NATURAL LANGUAGE MODE)`，ngram 索引已在 migration-v2.sql 建
- 失败自动降级 `LIKE %kw%`
- 返回结构 `{answer, references:[{id,title,source,snippet,score}], memoryUsed:10}`
- references 即出处，前端可展示来源
